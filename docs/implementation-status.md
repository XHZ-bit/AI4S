# Research Atlas 项目实施情况与现状报告

## 1. 报告信息

- 评估日期：2026-09-22
- 项目阶段：功能闭环 MVP / 比赛原型
- 评估范围：前后端代码、测试、README、设计文档和实施计划
- 当前结论：已经具备从论文数据进入知识图谱并生成科研路线的端到端基础，但还不是面向真实用户长期使用的完整产品。

## 2. 当前项目概况

当前项目名为 Research Atlas，首期面向具身智能和强化学习方向的科研新手，已经形成如下主流程：

```text
arXiv/本地 PDF
→ 论文解析
→ LLM 实体和关系抽取
→ embedding 实体对齐
→ 人工审核
→ Neo4j 知识图谱
→ 图谱浏览/语义检索
→ 个性化科研路线生成
→ 路线进度跟踪
```

现有代码目录已包含：

- `backend/app/collector`：论文采集；
- `backend/app/parser`：PDF 解析；
- `backend/app/pipeline`：抽取和实体对齐；
- `backend/app/graphsvc`：图谱查询和实体操作；
- `backend/app/roadmap`：路线算法和生成；
- `backend/app/search`：语义检索；
- `backend/app/api`：各模块 API；
- `frontend/src/pages`：图谱、论文详情、审核、数据管理和路线页面；
- `backend/tests` 和 `frontend/src/__tests__`：自动化测试。

## 3. 已实现功能

- FastAPI 健康检查接口存在；
- 前端 Vite 构建配置存在；
- 前后端 API 模块已按功能拆分。

### 当前限制

## 3.2 论文采集：已实现

### 已实现能力

- arXiv Atom 采集；
- 通过关键词、分类、起始年份和最大数量触发采集；
- Semantic Scholar 引用链回填模块；
- 论文元数据写入 SQLite；
- 论文数据同步到 Neo4j 的基础能力；
- 前端数据管理页可触发采集并展示论文列表。

### API

```text
POST /api/collect
GET  /api/papers
```

### 当前限制

- 采集覆盖范围仍以 arXiv 和已有连接器为主；
- 论文代码、复现实验和课程资源的自动整合尚未完整实现；
- 引用数量和引用增长等路线评分所需字段仍不完整或部分使用默认值；
- 采集任务没有持久化队列、取消和失败重试体系。

## 3.3 PDF 上传与解析：已实现基础闭环

### 已实现能力

- 本地 PDF 上传；
- 服务器端 PDF 魔数检查；
- 文件大小限制 50MB；
- UID 格式校验；
- GROBID TEI 结构化解析；
- PyMuPDF 降级解析；
- 标题和摘要写入论文表；
- 解析状态保存；
- 上传论文自动建立基础图节点；
- 论文摘要进入语义索引。

### API

```text
POST /api/papers/upload
GET  /api/papers/{uid}
GET  /api/papers
```

### 当前限制

- 主要解析标题、摘要和有限的引言片段；
- 尚未稳定支持全文按章节、公式、表格和图片的深度解析；
- 上传过程仍是同步处理，较大文件会影响请求时延；
- 尚无用户级文件隔离和删除/归档管理。

## 3.4 LLM 知识抽取：已实现

### 已实现能力

- 结构化 JSON 抽取；
- 7 类实体类型：Paper、Concept、Method、Dataset、Benchmark、Resource、Author；
- 9 类关系类型：CITES、PROPOSES、USES、EVALUATES_ON、IMPROVES_ON、COMPARED_WITH、PREREQUISITE_OF、HAS_RESOURCE、SUBTOPIC_OF；
- Pydantic schema 校验；
- 关系别名归一化；
- 实体置信度和关系置信度保存；
- 实体 embedding 生成；
- 抽取候选写入 SQLite proposal 表；
- 低置信度普通关系过滤；
- `PREREQUISITE_OF` 关系保留并进入人工审核。

### 当前实现特点

抽取服务已经体现出“模型生成候选、人工审核后入图”的质量控制思路，而不是直接把 LLM 输出写入图数据库。

### 当前限制

- 主要输入仍是标题、摘要和引言片段；
- 证据字段目前是抽取结果中的文本字段，尚未统一到页码、段落和字符区间；
- 模型置信度尚未通过人工标注集校准；
- 尚未建立实体/关系 Precision、Recall、F1 基准；
- 尚未形成对公式、实验设置和结论主张的独立抽取模型。

## 3.5 实体对齐：已实现原型

### 已实现能力

- 余弦相似度实体匹配；
- 可按实体类型过滤候选；
- 三段式分流：

```text
相似度 >= 0.85：自动合并
0.60 <= 相似度 < 0.85：人工确认
相似度 < 0.60：新建实体
```

- 新实体生成 canonical UID；
- 待审核实体保留对齐结果。

### 当前限制

- 仍是全量向量扫描，数据规模增长后效率有限；
- 尚未结合别名、上下文、论文来源和时间进行实体消歧；
- 自动合并没有完整的回滚和版本历史；
- 相似度阈值尚未基于领域标注集校准。

## 3.6 审核工作台：已实现基础功能

### 已实现能力

- 获取待审核队列；
- 按候选类型和论文过滤；
- 支持 approve、edit、reject；
- 通过实体候选后写入 Neo4j；
- 通过关系候选后写入 Neo4j；
- 建立论文与实体之间的 `MENTIONS` 关系；
- 保存候选状态。

### API

```text
GET  /api/review/queue
POST /api/review/{id}/decision
```

### 当前限制

- 前端主要展示候选 JSON，尚未实现原文证据高亮；
- 没有明确的拒绝原因、审核人和审核时间字段；
- 没有审核历史、回滚和多人一致性审核；
- 没有批量审核操作；
- 高置信度自动合并缺少定期抽检机制。

## 3.7 图谱存储与可视化：已实现

### 已实现能力

- Neo4j 实体和关系写入；
- 节点检索；
- 邻域子图查询；
- 图谱节点按类型着色；

- 基础搜索和类型过滤；
- 论文详情页展示关联节点数量和关系数量。

### API

```text
GET /api/graph/nodes
GET /api/graph/neighbors/{uid}
```

### 当前限制

- 目前更接近图谱浏览器，还不是完整的学习导航视图；
- 节点详情尚未展示原文证据、前置知识、用户掌握度和学习建议；
- 尚未实现图谱与个人学习状态的融合；
- 大图谱下缺少分页、聚类和按任务的局部视图。

## 3.8 语义检索：已实现原型

### 已实现能力

- 论文摘要 embedding 入库；
- 查询文本 embedding；
- 余弦相似度排序；
- top-k 返回；
- `/api/search?q=` 接口；
- 基础单元测试。

### 当前限制

- 当前以 SQLite 中的 embedding 做 Python 暴力扫描；
- 主要基于标题和摘要；
- 尚未实现 BM25、关键词检索、向量与图混合检索；
- 尚未支持按年份、作者、数据集、方法和资源过滤；
- 返回信息较少，尚未返回命中片段和命中原因；
- 尚未接入重排序模型。

## 3.9 个性化路线推荐：已实现核心原型

这是当前最接近项目核心价值的模块。

### 已实现能力

- 用户输入自然语言目标；
- 输入已掌握概念；
- 输入每周投入时间；
- LLM 解析目标概念；
- 通过 `PREREQUISITE_OF` 计算前置知识闭包；
- 使用拓扑排序生成学习顺序；
- 剔除用户已掌握节点；
- 为知识节点匹配论文；
- 根据教学评分选取论文；
- 沿 `IMPROVES_ON` 生成实验链；
- 输出创新点建议；
- LLM 将结构化骨架包装为阶段化路线；
- 路线结果写入 SQLite；
- 前端展示阶段、论文、实验和资源卡片；
- 支持勾选完成进度；
- 进度通过 PATCH 接口保存。

### 算法骨架

```text
目标定位
→ 前置依赖闭包
→ 拓扑排序
→ 已掌握节点剪枝
→ 论文评分
→ 实验改进链
→ 创新信号
→ LLM 生成路线文本
```

### 当前 API

```text
POST  /api/roadmap/generate
GET   /api/roadmap/{id}
GET   /api/roadmap
PATCH /api/roadmap/{id}/progress
```

### 当前限制

- 用户画像仍较简单，主要包含目标、已掌握概念和每周时间；
- 进度更新目前主要改变 done 状态，尚未基于结果重新规划；
- 缺少自测、任务完成标准和真实掌握度模型；
- 部分教学评分字段默认值为 0 或固定值；
- 目标实体解析使用名称匹配，尚未提供 Top-K 消歧确认；
- 实验链尚未完全保证基线到目标方法的时间和路径顺序；
- 创新信号目前属于原型规则，尚未经过真实科研专家验证；
- 推荐项 evidence 目前主要来自路线生成结果，尚未全部绑定到原文 span。

## 6. 当前最重要的产品差距

### 6.1 从“路线展示”到“学习闭环”

当前已经可以生成路线并勾选项目，但还不能充分回答：

- 用户是否真的理解了知识；
- 用户是否完成了实践；
- 用户哪里遇到困难；
- 下一阶段是否应该调整；
- 用户距离目标论文还有多远。

因此下一阶段应优先实现测验、任务完成标准和掌握度更新，而不是继续堆叠图谱节点数量。

### 6.2 从“候选 evidence”到“原文证据链”

当前抽取结果存在 evidence 字段，但还需要统一为：

```text
文档 → 页码 → 章节 → 段落/字符范围 → 抽取关系 → 审核记录
```

这是系统可信度和比赛说服力的关键提升点。

### 6.3 从“原型统计信号”到“可验证推荐”

当前路线评分和创新建议中，引用数、资源可用性、难度等数据存在默认值或简化统计。需要替换为真实字段，并为每个推荐输出原始证据和计算过程。

### 6.4 从“技术管理台”到“面向新手的产品”

当前页面更适合开发者操作。要吸引用户使用，需要增加：

- 新用户引导；
- 今日学习任务；
- 论文学习卡片；
- 证据解释；
- 成长进度；
- 一键继续学习；
- 任务失败后的补救建议。

## 7. 下一阶段实施优先级

### P0：必须优先完成

1. 建立真实的目标论文和领域知识种子集；
2. 为抽取结果保存页码、章节和原文 span；
3. 修正路线推荐中的引用、资源、难度和 benchmark 统计；
4. 给目标实体解析增加 Top-K 候选和用户确认；
5. 实现论文学习卡片；
6. 为每个路线项增加预计时间、完成标准和自测问题；
7. 完成后端测试环境修复和干净环境全量验证。

### P1：比赛效果提升

1. 建立普通 RAG、Hybrid RAG 和路线智能体对比实验；
2. 增加证据原文高亮；
3. 增加“资料不足/存在冲突”的提示和拒答；
4. 实现用户掌握度和任务反馈；
5. 增加首页、今日任务和成长看板；
6. 增加混合检索和方法/数据集/年份过滤；
7. 准备一套现场演示数据和固定演示脚本。

### P2：产品化建设

1. PostgreSQL 替换或补强 SQLite；
2. 持久化任务队列和重试机制；
3. 用户账号、权限和项目空间；
4. 大规模向量检索；
5. 多领域知识图谱扩展；
6. 真实用户留存和成长结果分析。

## 8. 建议的下一版验收标准

完成下一阶段后，至少应满足：

- 用户上传一篇目标论文后能看到前置知识图谱；
- 每个关键前置关系可定位到论文页码和原文；
- 用户输入目标和基础后能得到阶段化计划；
- 每个阶段至少有一项阅读任务和一项实践任务；
- 每个任务有完成标准；
- 用户完成任务或测验后，掌握状态会变化；
- 系统能根据掌握状态重新生成剩余路线；
- 无证据的问题会拒答或标记不确定；
- 至少用 20 个固定问题对比普通 RAG 和本系统；
- 关键指标、测试结果和演示数据能够复现。

## 9. 当前项目结论

Research Atlas 已经不是只有概念的项目，而是完成了知识图谱和路线推荐的技术 MVP。其最有潜力的差异化方向是：把 `PREREQUISITE_OF` 前置关系、论文知识结构和用户目标结合起来，生成科研学习路径。

但当前项目的核心产品价值还需要通过真实用户成长闭环来证明。下一阶段的重点不是继续增加抽取关系和页面数量，而是把以下链路做实：

```text
论文证据
→ 知识关系
→ 用户知识缺口
→ 可执行学习任务
→ 任务/测验结果
→ 掌握度变化
→ 路线调整
→ 用户真正读懂论文或完成复现
```

只有当用户能够完成目标论文阅读、基础实验复现或研究方向入门，平台才真正实现“以用户成长结果为评价标准”的产品目标。
