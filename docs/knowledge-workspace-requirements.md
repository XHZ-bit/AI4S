# PaperStride 独立研究空间需求分析

整理日期：2026-10-29。依据两轮需求交流、用户提供的研究报告及最终批准的《PaperStride 平台改进方案》整理。本文件用于保存需求背景、确认结果和验收边界；实现与使用方式见[交付说明](knowledge-workspace-release.md)，实测结果见[验收记录](validation/knowledge-workspace-2026-10-29.md)。

早期产品设想保留在[Research Atlas 产品需求文档](product-requirements.md)。本文细化本轮研究工作台，不将早期路线规划、测验或公开部署设想全部算入本轮交付。

## 1. 需求背景与第一轮交流

### 1.1 用户实际遇到的问题

第一轮交流由真实上传体验触发。已有示例能展示若干页面，但用户自己上传论文后，缺少从资料到知识的完整处理：论文没有形成可用的研究逻辑拆解，图谱未成为真实工作的组织方式。不同辅助页面虽然存在，页面之间的转移和操作不便，整体仍主要表现为一个附带辅助功能的论文阅读器。

原文阅读也存在基础问题：显示区域偏小、页面显示不完整、重复页面框架挤占空间。只有总结或侧栏解释，不能解决用户长时间核对全文、公式、图表和代码的需要。

由此形成四项基础需求：

| 问题 | 本轮应达到的结果 | 可观察的使用行为 |
|---|---|---|
| 上传后缺少分析 | 上传归入当前研究空间，并自动启动结构解析、知识抽取和建图 | 用户能看到原文、章节、知识节点及分阶段状态 |
| 图谱没有空间边界 | 每个研究空间具有独立知识组织和人工修订 | 同一论文在两个空间的修改互不影响 |
| 阅读窗口受限 | 原文成为宽屏主视图，连续阅读并准确定位 | 可完整阅读横向页、双栏页和长论文，按页码或证据跳转 |
| 平台价值分散 | 图谱贯通理解、学习、比较和研究记录 | 从方法差异进入知识学习，再返回比较位置 |

这些需求指向一个工作流程：**资料进入空间 → 解析成有来源的结构与知识 → 从图谱进入论文或方法 → 沿具体节点补充理解 → 核对原文和实现 → 回到研究比较与记录。**

### 1.2 图谱应承担的作用

图谱需要同时回答三类问题：这份资料研究什么、理解一个模块需要什么、不同资料与自己的方法有什么关系。因此不能只把论文标题连在一起，也不能把全部概念一次堆到画布上。

确认采用三个层次：

1. 空间总图：论文、自己的研究资料、共同研究问题和跨资料关系。
2. 单篇或方法拆解图：问题、贡献、方法模块、实验、结果和局限。
3. 知识节点：概念、公式、算法、符号、前置知识、依据和实现入口。

节点和关系都应可进入。关系名称表达“依赖”“组成”“用于”“比较”“支持该判断”等实际含义，关系详情能说明依据。画布只显示当前关注部分，完整知识通过搜索、筛选、单篇展开和节点邻域继续访问。

### 1.3 学习与阅读的关系

基础讲解应随节点准备，详细推导、资源和源码解释按需生成并保存。前置知识由用户按需要展开，不强制完成测验或固定课程后才能继续研究。

深入学习需要独立宽屏视图，承载直观解释、原文定义、公式与推导、前置知识、实现与演示、继续探索。讲解上下文应包含节点、论文相关内容、相邻知识及研究目标，避免只根据标题、摘要或一个片段泛泛说明。

阅读、图谱、学习和比较之间需要双向入口，并保留资料、节点、页码或内容块及返回位置。PDF、报告、代码、表格使用各自合理的定位方式，不能给 DOCX 或代码编造 PDF 页码。

## 2. 第二轮交流：结合真实研究澄清

### 2.1 研究材料与使用背景

用户提供了 `D:/storage/Codex_program/Arm/reports/idea_summary_20261028/臂手协同PPO论文探索阶段总结.docx`。报告用于了解 ArmHand_PPO 场景中的研究过程、方法版本和困难，包括 D1、D2、状态门控、跨分支消息、有界残差及相关实验陈述。

报告是用户主动提供的研究资料。报告中的目录、文件名和代码路径仅是内容，不能据此自动扫描、导入或执行本机文件。后续实施中用户明确：**个人资料仅导入这份原始 DOCX，不导入个人源码和结果文件**；公开 CoorDex 仓库用于源码查看与版本定位。平台仍提供手动选定代码和结果资料的能力，能力范围与本次实际导入范围分别记录。

报告的日期和方法状态必须保留。报告说某项实验已完成，表示“报告作出了这一陈述”，不表示平台独立重复实验或确认该陈述等于当前研究状态。

### 2.2 两条同等重要的研究任务

**任务 A：比较相关工作与自己的方法。** 从相关论文和研究报告出发，明确选择 D2 等具体方法，理解协调问题、策略划分、信息路径、观测、动作与控制、训练目标和额外成本、实验条件与结果、原论文与当前适配的差异。每项比较都能继续进入对应节点、原文或代码，再回到原比较。

**任务 B：从模块学懂数学与实现。** 从状态门控、有界残差等具体模块进入公式、符号、推导和前置知识，运行适用教学演示，查看实际已经提供的实现材料，再返回原文或比较位置。

两条任务都应贯通。只有论文摘要、对比文字或演示卡片，均不能单独算作完成。

### 2.3 比较内容与判断边界

| 比较维度 | 需要保留的信息 |
|---|---|
| 协调问题 | 任务目标、困难和方法试图解决的缺口 |
| 模块划分 | 共享主干、分支、策略、门控或消息模块各自作用 |
| 信息路径 | 信息从何处进入、流向何处、在哪个位置影响决策 |
| 输入与输出 | 观测范围、动作表达和低层控制方式 |
| 训练方式 | 目标、奖励、额外训练成本及适用假设 |
| 实验依据 | 任务、指标、评价条件、结果和缺失项 |
| 适配差异 | 原论文方法与自己实现或设想的对应关系 |

只有任务、指标和评价条件兼容时才能直接对照数值。不兼容时展示条件差异；缺少来源时保留未知。论文结果、自己的适配结果、报告中的历史陈述、平台归纳和教学示例应清楚区分。

### 2.4 自己的研究资料进入图谱

报告、方法说明、手动选定代码与结果应使用相同的来源和知识模型，成为图谱中的方法、模块、公式、实验或结果节点。资料中提及但未提供的实现和结果显示为待补充来源。

必须分开保存两个维度：

- 内容来源：原文明示、平台归纳、用户补充。
- 研究状态：未说明、设想、已实现、报告中已完成、待验证。

同名不等于同一实体。D1、D2、不同论文中的同名变量及缩写保留上下文；无法确定时先建立关联，由用户决定是否合并。人工合并应可拆回，隐藏应可恢复。

## 3. 确认后的产品组织

### 3.1 五个主要视图

| 视图 | 用户目的 | 必要衔接 |
|---|---|---|
| 研究图谱 | 从空间或单篇进入问题、方法与知识 | 节点、关系、原文、学习 |
| 原文阅读 | 连续阅读并核对证据 | 页码/内容块定位，原文返回节点 |
| 深入学习 | 理解知识在当前研究中的意义与实现 | 公式、前置节点、资源、演示、返回来源 |
| 方法比较 | 比较论文、自己的方法及条件差异 | 具体方法聚焦，节点与证据入口 |
| 资料与记录 | 添加材料、查看处理过程、保存研究记录 | 分阶段继续处理，修订与旧工作台记录 |

任务状态显示在资料和空间内，不强迫用户进入独立任务页确认处理是否完成。自动内容可以直接使用，并标明来源与性质；不增加逐条确认后才能使用的门槛。

### 3.2 三种空间模式

| 模式 | 默认讲解与推荐重点 |
|---|---|
| 零基础探索 | 补充直观说明和前置知识 |
| 已有思路深入研究 | 围绕研究目标、机制差异和方法联系 |
| 阅读与复现 | 强调原文、实现条件、源码和复现依据 |

模式按空间保存，可随时调整。调整模式不删除已有知识，也不关闭用户可能需要的功能。

新空间有 1—3 份资料时优先单篇焦点，达到 4 份时优先空间总览。用户明确选择后恢复其视图选择。画布按需展开，首轮性能目标以每空间 50 份资料验证；这不是知识总量截断。

### 3.3 来源与空间独立

同一账号相同内容可复用原文件及基础解析，各空间分别保存节点、关系、解释、学习结果、笔记、修订和隐藏状态。所有读取和修改校验账号、空间及来源归属。

重新分析追加处理结果与版本，不覆盖用户已经修订的字段。移除来源保留记录、版本和来源缺失提示，允许恢复资料。已保存学习和比较在依据变化后提示复核。

### 3.4 上传和处理

首轮需求包括 PDF，DOCX/Markdown/TXT，CSV/XLSX/JSON，选定代码文件，以及论文和公开仓库链接。上传直接归入当前空间，依次完成原文保存、结构解析、研究逻辑抽取和图谱更新。

“原文可读”“结构解析完成”“知识抽取完成”“图谱已更新”分别显示。正文成功而公式失败、结构图可用而语义未完成等情况显示部分完成，保留已完成成果并支持继续。重启中断后由用户继续，避免服务重启自动重复付费请求。

### 3.5 学习资源与首批演示

外部资料优先选用已登记教材、课程、官方文档、论文和官方仓库。实际获取内容才作为解释依据；只有链接时标为资源入口。

首批可复用演示为链式法则与计算图、sigmoid/tanh 输出与局部梯度、门控位置与有界残差、高斯策略均值与采样、PPO 比率与裁剪、共享主干与分支信息路径。演示显示输入、预期行为及简化条件，标注为教学内容。

Python 支持文件、类、函数、行号和版本定位；其他语言首先提供文本与来源定位。不承诺在缺少源码或语义对应依据时自动找到论文的精确实现。

## 4. 技术及运行约束

| 约束 | 本轮确认选择 |
|---|---|
| 使用方式 | 当前电脑本机完整流程优先，保留账号隔离 |
| 现有框架 | 保留 FastAPI、React、PDF.js |
| 核心数据 | SQLite 保存来源、知识、版本和任务，Neo4j 可作为重建投影 |
| 结构解析 | 新增 Docling 主流程；PyMuPDF 用于快速读取、裁片与兼容 |
| 模型管理 | 平台统一配置，记录来源版本、调用、用量、失败和缓存 |
| 运行默认值 | 每份基础分析最多 16 次请求；深入学习最多 4 次；外部模型并发 2；解析并发 1 |
| 超限和失败 | 已完成部分可用，显示缺失内容，用户继续处理 |
| 迁移 | 先备份，在独立副本验证；旧笔记、修订与快照保持历史含义 |

这些默认值是运行约束，不代表已测得的费用、速度或准确率。缓存浏览与节点详情的目标响应时间为 2 秒内，是否达到须有实际机器测量。

## 5. 验收范围与未包含范围

### 5.1 真实资料

验收采用 CoorDex、Reactive Grasping、Pixel2Catch、DexPBT，以及用户提供的原始研究报告。公开 CoorDex 代码仓库保存固定提交的选定文件快照，作为可检查实现来源；本次不导入个人代码和个人结果文件。

不得为四篇论文编写专属抽取分支；另选未参与规则调整的论文检查通用性。抽取覆盖、公式符号、关系依据、原文坐标、跨空间独立性、修订保护、中断恢复、演示数值和导航返回均需检查。真实质量、耗时、用量和未通过项目的结果见[验收记录](validation/knowledge-workspace-2026-10-29.md)。

### 5.2 不属于本轮的目标

- 公网正式部署与完整多人付费模型治理。
- 机器人完整训练、硬件实验和实验运行管理。
- 任意节点自动生成并运行任意交互实验。
- 自动提出并确认科研创新点。
- 把模型解析成功、公式可渲染、引文可定位等同于科学结论正确。

### 5.3 需求与交付的追溯

| 编号 | 核心需求 | 交付检查入口 |
|---|---|---|
| R01 | 上传后自动形成原文、结构和知识 | 资料与记录中的四阶段状态 |
| R02 | 独立空间、来源复用、修订保留 | 两空间同一资料的独立编辑与再分析 |
| R03 | 空间图→单篇图→知识节点 | 研究图谱、节点与关系检查器 |
| R04 | 宽屏完整原文与准确来源定位 | 原文阅读、证据跳转及返回 |
| R05 | 具体方法比较并继续探索 | 比较中选择报告 D2，进入节点或原文 |
| R06 | 数学、前置知识、代码和演示学习 | 节点深入学习主视图 |
| R07 | 来源性质与研究状态分开 | 节点标记、比较依据、报告日期与缺失来源 |
| R08 | 失败部分可用、继续处理和预算记录 | 分析任务、缓存、重启恢复与用量 |
| R09 | 保留旧数据和旧入口 | 迁移脚本、旧工作台与历史快照 |

需求文件说明“应当做到什么”；交付说明说明“代码如何提供功能”；验收记录说明“对哪些材料实际检查到什么结果”。三者分别保留，后续调整追加日期和依据。
